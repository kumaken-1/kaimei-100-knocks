# 100本ノック全体チューニング設計

## 目的

承認済みの最初の10問を文章基準とし、残り90問をケース固有の内容へ個別編集する。同時に、利用者が選んだ判断とフィードバックを結びつけ、「自分の判断を仮置きする → その判断の価値を知る → 別の見方に触れる」という学習の往還をアプリ上で成立させる。

## 成功条件

1問を終えた利用者が、選んだ判断の背景にある価値を理解し、最初には見ていなかった事実・立場・条件を一つ以上説明できること。

## 対象範囲

- 最初の10問の承認済み原稿をアプリ用データへ反映する。
- 残り90問を10問単位で個別編集する。
- 100問すべてに選択別フィードバックを追加する。
- 回答後の表示を、選択内容に応じて切り替える。
- 深掘り4項目を折りたたみ表示にする。
- データ完全性、重複、保存互換性、画面表示を検証する。

今回は得点化、自由記述、回答後の自己評価、利用者間の共有機能は追加しない。

## コンテンツ構造

各問題は次の情報を持つ。

```js
{
  id: "knock-001",
  groupId: "group-01",
  theme: "授業を見るものさし",
  context: "子どもや学校の具体的な事実",
  prompt: "判断を仮置きする問い",
  choices: [
    {
      id: "plan",
      label: "選択肢の表示文",
      feedback: {
        value: "この判断が大切にしていること",
        check: "同時に確かめたいこと"
      }
    }
  ],
  perspective: {
    title: "視点をひらく見出し",
    body: "ケースに固有の共通解説"
  },
  deepDive: {
    perspective: "別の読み方",
    evidence: "確かめたい事実",
    experiment: "小さく試すこと",
    condition: "判断を変える条件"
  }
}
```

選択別フィードバックは `value` と `check` を分けて保持する。これにより、文章上の役割を検査でき、画面でも二つの観点を明確に表示できる。

## ファイル構成

100問を一つの巨大なファイルで管理せず、領域ごとの10ファイルへ分割する。

- `js/question-groups/group-01.js` — 問01〜10 基本の10問
- `js/question-groups/group-02.js` — 問11〜20 見取り・評価
- `js/question-groups/group-03.js` — 問21〜30 個別と協働
- `js/question-groups/group-04.js` — 問31〜40 問い・探究
- `js/question-groups/group-05.js` — 問41〜50 授業設計
- `js/question-groups/group-06.js` — 問51〜60 校内研究
- `js/question-groups/group-07.js` — 問61〜70 教育課程
- `js/question-groups/group-08.js` — 問71〜80 ICT・生成AI
- `js/question-groups/group-09.js` — 問81〜90 学校づくり
- `js/question-groups/group-10.js` — 問91〜100 多様な学び
- `js/questions.js` — グループ情報と10ファイルの結合・公開だけを担当

現在の `LENSES`、`DEEP_DIVE_BUILDERS`、`EXPANSION_SEEDS`、`expandQuestion` による文章生成は、100問の個別データへの移行完了後に削除する。

## 編集原則

### 選択肢

- 3案を優劣の順に並べない。
- どの選択肢にも、守ろうとしている教育的価値を持たせる。
- 最も長い選択肢だけが正解に見えないよう、文量をそろえる。
- 「両方見る」だけの万能な第3案を繰り返さない。

### 選択別フィードバック

- `value` は、その判断が守ろうとしている価値を一文で示す。
- `check` は、その判断だけでは見落とす可能性があるケース固有の事実を一文で示す。
- 回答者を褒めたり否定したりしない。
- 「正解」「不正解」「間違い」「よい選択」と評価しない。
- 他の問題へテーマ名だけ差し替えて使える文章にしない。

### 共通解説と深掘り

- ケース中の発言、行動、成果物、前後の変化へ戻る。
- 一つの事実に少なくとも二つの読み方を置く。
- `evidence` は誰の何を見るかを明示する。
- `experiment` は一人・一場面・一回など、すぐ試せる単位にする。
- `condition` は観察可能な条件文にする。
- 学校の制度や教師の意図だけでなく、子どもの事実を判断根拠に含める。

## 画面表示

回答前は現在と同じく、ケース、問い、3択、「視点をひらく」ボタンを表示する。

回答後は次の順序で表示する。

1. 「この判断が大切にしていること」— 選択した回答の `feedback.value`
2. 「同時に確かめたいこと」— 選択した回答の `feedback.check`
3. 「視点をひらく」— 全回答に共通する `perspective`
4. 「もう一段、見方を増やす」— `deepDive` の4項目

選ばなかった二つの回答へのフィードバックは表示しない。深掘り4項目はネイティブの `<details>` と `<summary>` を使用し、初期状態では閉じる。キーボード操作と標準の開閉状態を保ち、独自JavaScriptで折りたたみを再実装しない。

## データフロー

1. 利用者が選択肢を選び、送信する。
2. 現在と同じ形式 `{ choiceId }` で端末内へ保存する。
3. `choiceId` から該当する選択肢を取得する。
4. 該当選択肢の `feedback.value` と `feedback.check` を表示する。
5. 共通解説と深掘りを表示する。
6. 回答済み問題を開き直した場合も、保存済み `choiceId` から同じ内容を再表示する。

保存形式は変更しないため、既存利用者の回答と進捗を引き継げる。

## 不正データへの対応

- 問題に存在しない `choiceId` が保存されている場合、その回答は未選択として扱い、選択別フィードバックを表示しない。
- `feedback` が欠落した問題はテストで失敗させ、公開データへ混入させない。
- 100問のID、グループ、並び順は現在のものを維持する。

## 実装順序

1. 選択別フィードバックを必須とする失敗テストを追加する。
2. 問01〜10を新データ構造へ移行する。
3. 選択内容に応じて表示するUIを実装する。
4. 既存保存データから再表示できることをテストする。
5. 問11〜100をグループごとに個別編集する。
6. 旧テンプレート生成処理を削除する。
7. 全体の重複・文章量・必須項目を自動検査する。
8. デスクトップとスマートフォンで表示を確認する。

## 自動検証

次をテストする。

- 問題数が100でIDが一意である。
- 各問に3択がある。
- 全選択肢に空でない `feedback.value` と `feedback.check` がある。
- 100問すべてに `perspective` と `deepDive` の4項目がある。
- 選択した `choiceId` に対応するフィードバックを取得できる。
- 存在しない `choiceId` ではフィードバックを返さない。
- 既存形式の保存データを読み込める。
- ケースと問いが100件とも固有である。
- 選択別フィードバック600文、共通解説100件、深掘り各100件に完全一致の重複がない。
- 旧テンプレート生成定数と関数が残っていない。
- 必須DOM要素、フォーカス移動、折りたたみ要素の構造が保たれている。

## 目視検証

- デスクトップ幅と390px幅で横スクロールが発生しない。
- 回答後、選択した回答へのフィードバックが最初に読める。
- 別の選択肢へ回答を変更すると、表示内容も変わる。
- 深掘りが初期状態で閉じ、マウスとキーボードの両方で開閉できる。
- 長い日本語が見出し、カード、ボタンからはみ出さない。
- 一問を読む負担が、現在より不必要に増えていない。

## 完了条件

- 100問が個別編集済みで、旧テンプレート生成処理が削除されている。
- 選択した回答に固有のフィードバックが表示される。
- 既存の回答・進捗が維持される。
- 自動テストと目視検証がすべて成功する。
- 公開前に変更内容をコミットし、Kenさんの確認を受ける。
